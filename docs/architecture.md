# Architecture and lifecycle

The core library holds the event schema, EventBus, configuration, snapshot diff algorithms, process tracker, rules, correlator, risk scorer, JSONL output, metrics and replay. Win32 collectors link into the single CLI. UTF-8 strings replace the plan's suggested internal wstrings: Win32 boundaries convert with strict UTF-16/UTF-8 validation, keeping JSON and portable tests consistent. Related headers are consolidated into `Event.hpp`, `IMonitor.hpp` and `Diff.hpp`; the three native collector implementations remain separate.

Collectors own their threads and handles. ETW owns a unique GUID/name and starts a real-time system logger with process flags. EVENT_RECORD callbacks read named TDH properties with metadata-backed string types and copy bounded payloads to the queue. Created PID comes from ProcessId, never the ETW header PID. DCStart is marked as initial enumeration; DCEnd is ignored. Callback work contains no disk logging, enrichment, JSON, or rule execution. A consumer thread calls ProcessTrace; a five-second health thread queries ETW event/buffer loss. Dispatcher enrichment uses PROCESS_QUERY_LIMITED_INFORMATION, validates creation against event time, and queries full image path. Failures leave fields null.

TCP polling queries AF_INET and AF_INET6 with TCP_TABLE_OWNER_PID_ALL, bounded allocation retries and network-order port conversion. One complete snapshot must succeed for both families before the diff advances. The endpoint key includes family/protocol, addresses (including IPv6 scope), ports, owner PID, and known creation time. State is a compared dimension: transitions emit one `state_changed` observation rather than a synthetic close/open pair. Initial observations carry `first_snapshot=true`. Failures preserve the previous successful table. Process-time lookups that identify a generation created after snapshot start are discarded.

One persistent registry thread manages asynchronous notifications. Every watched target is reached through an existing ancestor handle, including missing or deleted Run keys. Registrations use REG_NOTIFY_THREAD_AGNOSTIC and are rearmed only after the event is consumed. Rearm occurs before rescan; burst rescans coalesce for 250 ms. Five-second reconciliation handles replacement/races, and retries preserve prior state on failures. Run/RunOnce enumerate all named values in each configured WOW64 view. Services enumerate only direct child keys and ImagePath/Start/Type; SYSTEM is shared across views, so it is scanned once. Baselines never become synthetic value additions. The root service key also participates in key diff. Values compare type plus raw representation; UTF-16 strings and little-endian DWORDs are decoded safely, other types remain raw. No writer attribution is inferred.

The bounded mutex/condition-variable EventBus drops newest on overflow and counts all losses. Queue close wakes waiters and drains accepted events. Logging is synchronous on the dispatcher, so there is no second unbounded disk queue. Slow storage can cause collector queue drops, which are surfaced on stderr and in health JSON. JSONL writes occur under one lock and flush each 64 event lines, at five-second dispatcher health updates, each alert, and shutdown. Health/session documents use a temporary file plus atomic replacement. Output files must be new and inherit a private protected DACL.

All event timestamps use RFC3339 UTC with exactly three fractional digits. Steady-clock receipt time is kept in memory separately and is not serialized. Replay validates all bounded input before starting, retains input arrival order, advances a monotonic virtual event-time watermark, and uses input event IDs. No live source is instantiated in replay. Lines/events are bounded to 1 MiB, replay files to 64 MiB/100,000 events, and parsed JSON depth to 32. Replay event/alert output is deterministic for the same input; the final state also tolerates reordered arrivals within the active time window, although intermediate escalation sequences can differ. Session metadata deliberately has no wall-clock stop time in replay and records the chosen output directory, so metadata from different output directories naturally differs.

The correlator retains at most `max_history_events` (4096 default) for `context_retention_seconds` (300). On relevant events it rebuilds time-sorted process generations and active evidence; this conservative bounded algorithm reconciles late parent/start observations without irreversible false joins. Process identity is PID+creation time, or a lower-confidence observed generation. Resolution considers start, exit and subsequent PID generations. Initial parent records can support a later child's ancestry if their creation times are known; rundown children cannot assert observed ancestry.

Active scoring evidence uses the most recent `correlation_window_seconds` (120), with independent narrower windows in correlation rules. Incidents group a verified Office lineage, otherwise a single process generation, otherwise a single registry artifact (hive/path/value/view). Registry artifacts attach only when one suspicious lineage has an identical unambiguous normalized executable path; ambiguous or missing paths remain standalone. Same-process correlation requires every condition on one identity, including a verified socket owner creation time. Path linkage lowers overall confidence and explicitly preserves unknown writer attribution. Distinct rule IDs contribute once; complete correlation bonuses contribute once; score is capped at 100. Expired incidents are removed from active memory and the alert suppression map; historical alerts remain on disk.

This implementation intentionally bounds history and recomputes evidence rather than maintaining an unbounded endpoint graph. Cost rises with history and rule count; eviction metrics identify coverage loss. Long-running process starts can expire, making later ownership/ancestry unknown until another usable process observation is received. This is a documented conservative v0.1 limitation.
